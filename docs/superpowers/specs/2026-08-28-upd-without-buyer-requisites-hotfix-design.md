# УПД без реквизитов покупателя — дизайн hotfix

## Цель

Кнопка «УПД» в списке заказов должна одним нажатием выпустить и открыть УПД выбранного клиента за выбранный день, даже если у покупателя не заполнены юридическое название, ИНН, КПП, ОГРН, юридический адрес, банк и договор. Продавец, ставка НДС, нумерация и аудит при этом должны оставаться однозначными и сохранёнными.

## Подтверждённая причина

Проблема состоит из двух независимых барьеров:

1. `UpdClientButton` сразу открывает GET `/production/print/upd/pdf?clientId=...&date=...`. Этот GET только читает уже созданные `UpdDocument`; при нулевой выборке он возвращает текст с фотографии и никогда не вызывает выпуск.
2. Валидация клиента считает `defaultOurLegalEntityId` частью реквизитов покупателя. Поэтому без ИНН нельзя сохранить нашего продавца, новые заказы получают `Order.ourLegalEntityId = null`, а генератор УПД исключает их.

Сам PDF уже поддерживает пустые реквизиты покупателя: название заменяется `Client.name`, адрес и ИНН — прочерками. `UpdBuyerSnapshot` и поля `Client` nullable; схема `UpdDocument` требует только целые JSON-снапшоты и конкретного нашего продавца.

## Рассмотренные варианты

### 1. Изменить только валидацию клиента

Плюс: минимальная правка. Минусы: кнопка продолжит печатать только ранее выпущенное; уже созданные заказы сохранят `ourLegalEntityId = null`; пользователь должен вручную исправлять клиента, заказ и отдельно выпускать УПД. Требование с фотографии не закрывается.

### 2. Выпускать УПД внутри GET PDF

Плюс: ссылка остаётся простой. Минусы: GET начинает менять БД и выдавать номера документов; повторные открытия, префетч и внешние проверки получают скрытый side effect. Ошибки выпуска невозможно нормально показать в исходной странице. Вариант отклонён.

### 3. Подготовить УПД Server Action, затем открыть read-only PDF — выбран

Клиентская кнопка синхронно открывает пустую вкладку, вызывает авторизованный Server Action через POST и только после успешного идемпотентного выпуска направляет вкладку на существующий GET PDF. Action получает `date + clientId`, поэтому не выпускает документы других клиентов.

## Архитектура и поток данных

1. Валидация `Client` разрешает `defaultOurLegalEntityId` при пустом ИНН. Остальные частично заполненные реквизиты покупателя по-прежнему запрещены.
2. `generateAndGetUpdForDate(dateIso, clientId?)` сохраняет старый пакетный режим без `clientId` и добавляет узкий режим клиента.
3. Перед выборкой групп узкий режим находит подходящие заказы клиента с `ourLegalEntityId = null`.
4. Продавец разрешается в строгом порядке:
   - активный `Client.defaultOurLegalEntityId`;
   - если его нет — единственное активное `OurLegalEntity`;
   - если активных продавцов ноль или больше одного — выпуск прекращается с понятной ошибкой, без номера УПД и без изменения заказов.
5. Для единственного продавца транзакция заполняет только ещё пустые snapshot-поля заказов, при необходимости сохраняет его как default клиента и пишет `ActivityLog`. Уже выбранного продавца она никогда не меняет. Это допустимо и после lock: заказ с `ourLegalEntityId = null` физически не мог попасть в `UpdDocument`.
6. Существующий генератор группирует только выбранного клиента, атомарно получает номер, сохраняет снапшоты и переиспользует документы по бизнес-ключу. Конкурентный повтор остаётся защищён `P2002`.
7. Кнопка закрывает пустую вкладку и показывает toast при бизнес-ошибке/исключении; при успехе открывает read-only PDF.

## Целостность и ошибки

- `UpdDocument.ourLegalEntityId` не становится nullable.
- При двух активных продавцах код ничего не угадывает.
- Автозаполнение использует условие `ourLegalEntityId: null`, поэтому не перетирает параллельное/ручное назначение.
- Нумерация остаётся внутри существующей транзакции `getNextDocumentNumber`.
- GET PDF остаётся read-only и сохраняет старые режимы `id`, `date`, `clientId + date`.
- Пустые реквизиты покупателя замораживаются как `null`; PDF явно рендерит fallback.
- Изменений схемы БД и миграций нет.
