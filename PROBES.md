# PROBES — план write-проб Бориса-Директа (НЕ исполнять без пробы + добра владельца)

Правило проекта: любая НОВАЯ write-структура API — только после пробы на ОДНОРАЗОВОЙ
ТЕСТОВОЙ кампании, незнакомую структуру не угадывать. Правки живой кампании 711897777 —
только после пробы + достаточных данных + явного «да» владельца. Разрешённый write-набор
Бориса при этом НЕ расширяется автоматически: сначала проба, потом (если ок) добавление в
`write-gate` отдельным решением.

Обозначения: 🧪 «проверить на тесте» — структура/значение не подтверждены нашими боевыми
пробами; ✅ — подтверждено разведкой «Прозрения».

**После волны аудита (07–09.07) — обе пробы В СИЛЕ, статус не изменился:** ни `bidmodifiers.add`
(проба A), ни `adgroups.update`-NegativeKeywords (проба B) в разрешённый write-набор НЕ введены —
групповые минуса всё ещё ВНЕ набора. ВАЖНО про минус-write на ЖИВОЙ 711897777: с merge `9701b08`/
`2c972ef` добавление минусов идёт ТОЛЬКО через единую точку `addNegativeKeywords` (свежий live ∪
новые, fail-safe), а удаление — через `removeNegativeKeywords` (удаляет из свежего live только
`added`). Прямой замещающий `campaigns.update(NegativeKeywords)` на живой кабинет напрямую НЕ
звать (стирает ручные правки) — только set-exact внутри гейта. Проба B ниже (шаги 2/4) описывает
СТРУКТУРУ транспорта на ТЕСТОВОЙ кампании; при переносе на живую — через гейтовые пути, не raw.

## Проба A — MobileAdjustment (понижающая корректировка мобайла)

**Зачем:** живой кабинет — мобайл 1672 ₽ / 6 кликов / **0 заявок** (десктоп даёт все заявки),
понижающей корректировки нет. Диагноз DEVICE_SKEW это и предлагает. Проба выверяет структуру
`bidmodifiers.add/get/delete`, чтобы потом применить на живой (или ввести в write-набор).

**Тестовый объект:** одноразовая ПУСТАЯ кампания (создать в интерфейсе Директа — так проще и
безопаснее, чем `campaigns.add` по API; поставить на паузу, бюджет минимальный). Записать её
`CampaignId` → это `<TEST_ID>`. Кампанию 711897777 в пробе НЕ трогать.

**Порядок (read-only контроль до и после каждого write):**

1. **Снять baseline:** `bidmodifiers.get` по `<TEST_ID>` (структура ✅ по разведке):
   ```
   bidmodifiers.get {
     SelectionCriteria: { CampaignIds: [<TEST_ID>], Levels: ['CAMPAIGN', 'AD_GROUP'] },
     FieldNames: ['Id','CampaignId','AdGroupId','Type','Level'],
     MobileAdjustmentFieldNames: ['BidModifier','OperatingSystemType']
   }
   ```
   Ожидаем пусто (корректировок нет).

2. **Добавить корректировку** (🧪 структура add + значение BidModifier):
   ```
   bidmodifiers.add {
     BidModifiers: [
       { CampaignId: <TEST_ID>, MobileAdjustment: { BidModifier: <N> } }
     ]
   }
   → ответ { AddResults: [ { Id: <modifierId> } ] }   // это те самые «Ids» (массив)
   ```
   - `BidModifier` — процент корректировки. 🧪 **Точную кодировку ПОНИЖЕНИЯ (диапазон и знак:
     0–100 «показывать на N% ставки» vs иная схема) выверить по `get` сразу после `add`** —
     не угадывать. Цель — понизить мобайл (например до −50% относительно базовой).
   - Из ответа сохранить `AddResults[].Id` → `<modifierId>`.

3. **Проверить `bidmodifiers.get`** снова — убедиться, что корректировка появилась, `Type` =
   мобайл-корректировка, значение `BidModifier` соответствует задуманному понижению.

4. **Удалить** (чистка теста):
   ```
   bidmodifiers.delete { SelectionCriteria: { Ids: [<modifierId>] } }
   ```
   `get` ещё раз → пусто. Тестовую кампанию удалить/оставить на паузе.

**Выход пробы:** подтверждённая структура add + кодировка BidModifier для понижения. Только
после этого — предложение владельцу применить на 711897777 (или добавить `bidmodifiers.add`
в разрешённый write-набор через write-gate). Риск применения на живой: средний, обратимо
(delete возвращает как было). Кампанию-цель до «да» владельца не трогать.

## Проба B — разгрузка G8: перенос минусов «сотрудник»-семейства на уровень ГРУПП

**Зачем:** вся минусовка живёт на уровне КАМПАНИИ (у всех 4 групп `NegativeKeywords: null` ✅).
Часть кампейн-минусов «сотрудник»-семейства режет живой трафик группы **G8 «Сотрудники»**
(это ровно кейс диагноза GROUP_MINUS_GAP). Кампейн-минус бьёт по ВСЕМ группам — надо перенести
такой минус на уровень тех групп, где он мусор (G1/G2/G4), сняв с кампании; G8 при этом
раскрывается.

**Предусловие (критично — не с потолка):** взять КОНКРЕТНЫЕ фразы из вывода диагноза
**GROUP_MINUS_GAP** Бориса (когда пойдут данные) — он называет точную пару «минус кампании X →
задел конвертящий запрос Y группы G8». НЕ двигать всё «сотрудник»-семейство скопом: слово
«сотрудник» может быть ЛЕГИТИМНЫМ и для G1 («питание для сотрудников офиса») — тогда групповой
минус в G1 задел бы уже G1. Для каждой фразы решить пофразно: в каких группах она мусор, в
каких — цель.

**Тестовый объект:** та же одноразовая тестовая кампания с 2–3 группами (или отдельная) —
выверить структуру группового `NegativeKeywords` на write, которого наши пробы не делали.

**Порядок (ГРУППЫ — ПЕРВЫМИ, потом снятие с кампании; иначе на шаге между откроется мусор):**

1. **Снять baseline:** `getCampaignSettings` (живой список кампейн-минусов ✅) + `adgroups.get`
   с `NegativeKeywords` по группам ✅. Зафиксировать текущее.

2. **Добавить групповые минуса** в те группы, где фраза — мусор (например «аксиома питание
   для сотрудника» = конкурент → минус в G1/G2/G4, но НЕ в G8). 🧪 **Структура `adgroups.update`
   для `NegativeKeywords` — проверить на тесте** (по аналогии с кампанией — список ЗАМЕЩАЮЩИЙ,
   слать объединённый набор):
   ```
   adgroups.update {
     AdGroups: [ { Id: <G1_id>, NegativeKeywords: { Items: [ ...текущие + новые... ] } } ]
   }
   ```
   Повторить для нужных групп. `adgroups.update` НЕ трогает TextCampaign → ADD_METRICA_TAG не
   слетает на этом шаге.

3. **Проверить** `adgroups.get` — групповые минуса на месте; прогнать день, убедиться, что
   G8 стала показываться по своим «сотрудник»-запросам (были заблокированы кампейн-минусом),
   а G1/G2/G4 не открыли мусор и не потеряли свой трафик.

4. **Только теперь снять с КАМПАНИИ** — `campaigns.update` с УМЕНЬШЕННЫМ списком (замещает
   целиком, слать полный список без перенесённых фраз) ✅ (структура кампейн-минусов
   подтверждена боевыми пробами):
   ```
   campaigns.update { Campaigns: [ { Id: 711897777, NegativeKeywords: { Items: [ ...без «сотрудник»-семейства... ] } } ] }
   ```

5. **Вернуть ADD_METRICA_TAG=YES** — после ЛЮБОГО `campaigns.update` по TextCampaign слетает в
   NO; здесь `campaigns.update` по `NegativeKeywords` живёт на верхнем уровне Campaign, но
   правило соблюсти строго: сразу после — `restoreMetricaTag` (проверить `getAddMetricaTagValue`
   = YES). ✅

**Риски:** (а) обратный порядок (снять с кампании раньше групп) на промежутке откроет мусор
всем группам — строго группы первыми; (б) групповой минус, добавленный «широко», может задеть
ЛЕГИТИМНЫЕ запросы самой группы — брать только фразы из GROUP_MINUS_GAP пофразно; (в) забыть
вернуть ADD_METRICA_TAG → слёт атрибуции заявок. Обратимость: полная (шаги симметричны —
groups.update/campaigns.update замещают списки; можно вернуть baseline из шага 1).

**Выход пробы:** подтверждённая структура группового `NegativeKeywords` на write. Применение на
живой 711897777 — пофразно, по выводу GROUP_MINUS_GAP, после «да» владельца; в write-набор
`adgroups.update` вводить отдельным решением после успешной пробы.

## Общий инвариант обеих проб
Тестовая кампания — одноразовая, удаляется после. Кампания 711897777 — БЕЗ write до отдельного
«да» владельца по конкретной правке. Токены — из env, не выводить. Каждый write в пробе —
через `write-gate` (в LIVE-режиме теста) с логом до/после, чтобы откат был тривиальным.
